# Release 2.27.0

适配 Minecraft 1.21.11 的非官方第三方版本。本次发布聚焦**资金安全、高并发稳定性与输入安全性**，修复了多类可能导致金币凭空消失或被刷出的缺陷。

> 🔴 **破坏性变更（不向后兼容）**：本次修改了跨服同步的数据报文结构（签名位置变更）。所有参与跨服同步（BungeeCord / Redis）的服务器**必须同时升级到 2.27.0**，否则跨服同步将不生效。

---

## 🔴 破坏性变更

- **跨服同步协议变更**：为防止客户端伪造同步数据，签名（sign）现置于反序列化**之前**校验，报文结构由 `version + object` 调整为 `version + sign + object`。新旧版本无法互通同步数据。

---

## 🔒 资金安全（防丢币 / 防刷币）

- **缓存丢失更新（lost update）**：余额变更引入 per-UUID 锁，串行化“读取-计算-写缓存”流程，消除高并发下同一玩家余额被覆盖错乱。
- **落库失败不再被静默吞掉**：异步写库失败即失效对应缓存，下次读取从数据库获取真实余额，避免缓存长期保留未被持久化的错误数值（此前存款落库失败会丢币、取款落库失败会刷币）。
- **非玩家账户改原子增量**：非玩家账户写库统一为数据库原子 `balance +/- ?`，修复缓存开启时用绝对值覆盖导致的丢失更新丢币。
- **清缓存逻辑修正**：移除“无在线玩家即清空全部缓存”等逻辑，修复异步落库尚未完成时清缓存导致下次读取拿到旧值而丢失余额变更；批量操作的清缓存移至写库成功之后。
- **拒绝负金额**：Vault / EnterpriseWallet / XConomyAPI 的存取款接口拒绝负数、NaN、Infinity（此前 `withdraw(player, -x)` 会使余额凭空增加，即刷币）。
- **`/pay` 加固**：发送方扣款采用原子余额校验，消除“检查余额”与“实际扣款”之间的 TOCTOU 透支；两次余额变更连续完成后再发送提示消息，避免消息异常导致“已扣款却未入账”。

## 🛡️ 安全（不信任客户端任何输入）

- **同步签名提前校验**：恶意客户端无法再通过自定义 payload 伪造 `xconomy:aca` 同步消息篡改任意玩家余额（刷币），同时堵住 Java 原生反序列化攻击面。
- **Redis 共享 KV 加签名**：Tab 列表等共享数据的反序列化同样前置签名校验，防 Redis 被注入触发反序列化。
- **弱签名启动警告**：`SyncData.sign` 为空 / 过短 / 默认值 `aa` 时输出严重警告（签名是防止伪造的关键防线）。
- **命令金额校验强化**：`isDouble` 统一拒绝负数金额。

## 🐛 逻辑修复

- 修复 `EnterpriseWallet.has()` 永远返回 `false` 的逻辑错误（原实现为余额与自己比较）。
- 修复 `EnterpriseWallet.setBalance` 方法名拼写错误（运行时会抛 `NoSuchMethodError`，此前被旧 class 文件掩盖）。

## ⚡ 并发稳定性

- **数据库连接**：未启用连接池时强制同步落库（避免多线程共享单一 Connection 造成 SQL 语句交错与数据损坏）；重连改为加全局锁 + 双重检查，防止高并发下反复关闭/重建连接池的连接风暴。
- **排行榜并发**：`baltop` / `baltop_papi` / `sumbalance` 改用并发容器与 `volatile`，防止异步刷新与读取并发时抛 `ConcurrentModificationException`。
- **跨服同步落地与权限状态**：`PlayerData.SyncStart` 复用 per-UUID 锁；`PermissionINFO` 改并发容器，`globalpayment` 加 `volatile`。
- **SQL 连接 null 全量防护**：所有数据库操作补充连接获取失败的 null 检查，避免数据库故障时 NPE 沿资金路径传播崩溃、导致玩家经济不可用。

## 📌 升级与配置建议

1. **跨服同步**：所有服务器需同时升级到 2.27.0。
2. **同步签名**：请将 `config.yml` 的 `SyncData.sign` 设置为**不少于 12 位的随机字符串**，切勿使用默认值 `aa`。签名是防止客户端伪造同步数据篡改余额的关键防线。
3. 数据库仍以 MySQL 为主，建议启用连接池（`usepool: true`）以获得更好的并发性能。

## ⚖️ 已知限制

- `/pay` 转账采用“缓存优先 + 异步增量落库”架构而非单一数据库事务，极端数据库故障时序下理论上存在极低概率的丢币可能；已通过原子余额校验、变更顺序、落库失败失效缓存等多重机制将风险降到极低。
- 余额列仍为 `double(20,2)`（每次写入按 2 位小数 round，非刷币/丢币来源）。如需更高精度可后续迁移到 `DECIMAL(20,2)`（涉及表结构变更）。

## 🔧 后续：热路径性能优化（2026-07-30，维护者 ZTF3）

在 2.27.0 安全/稳定性的基础上，对纯 Java 高频热路径做了**行为等价**的性能优化（红线：不触碰并发锁、跨服签名、SQL 落库等安全关键路径）：

- `DataFormat.shown` / `PEshownf` 增加按值 LRU 结果缓存 —— 真实负载命中率近 100%，余额展示吞吐 **17×–25×**。
- `CommandCore.isDouble` 消除每次调用编译正则 —— **1.83×**。
- `DataCon` 读路径合并 `containsKey+get` 为单次 `get` —— **1.51×**。
